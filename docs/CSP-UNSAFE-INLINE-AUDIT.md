# CSP `unsafe-inline` audit

_Date: 2026-10-01 · Scope: `server.js` `CSP_BASE` + `vercel.json` + `public/_headers` · Status: analysis + safe-only notes (no policy weakened)._

## TL;DR

- **`script-src` is already hash-based and carries NO `'unsafe-inline'`.** This is the strong state we want and it is enforced in CI. Nothing to do here except keep it that way.
- **`style-src` still has `'unsafe-inline'`** (`'self' 'unsafe-inline' https://fonts.googleapis.com`) in all 11 policy variants. Removing it today **would break the app** because the UI relies heavily on inline `style="…"` attributes (many set dynamically from JS). This doc lays out a progressive path; it does **not** remove it now.

## How the CSP is built

- `server.js` → `CSP_BASE` (lines ~117–132) defines the base directives. Per-page variants (`userImg`, `studio`, `invite`, `builder`) only relax `img-src`/`media-src`/`script-src`/`frame-ancestors` — never `style-src`.
- Inline **script** hashes are computed from the on-disk `public/*.html` by `scripts/csp-hashes.cjs` and injected at request time via `withHashes(...)`. `withHashes` also **strips any `'unsafe-inline'` from `script-src`** and drops stale hashes, so an accidental re-introduction is removed automatically.
- `vercel.json` + `public/_headers` carry the same hash list, generated by `npm run gen:csp` and verified in CI by `npm run check:csp` (`scripts/gen-csp.mjs --check`). `test/headers-parity.test.mjs` fails if server.js and vercel.json/_headers drift.

## Finding 1 — `script-src` (GOOD, no action)

`script-src` = `'self'` + a list of `'sha256-…'` hashes (one per inline `<script>`) + `https://cdnjs.cloudflare.com` + `https://browser.sentry-cdn.com` (+ `https://cdn.jsdelivr.net` on the builder page only).

Verified:

- `grep -c "script-src[^;\"]*unsafe-inline" vercel.json` → **0**.
- `npm run check:csp` → `✓ CSP script hashes current (45 inline scripts, 11 policies)`.
- `grep -rEo 'on(click|load|error|change|input|submit|mouseover)="' public/*.html` → **0** inline event handlers (these cannot be hash-covered and would force `'unsafe-inline'` back; keeping them at zero is what lets `script-src` stay hash-only). `test/csp-hashes.test.mjs` pins this: `gen-csp --check` fails on an inline event handler or `javascript:` URL.

**Action: none.** Keep inline scripts hash-covered; never add inline `on*=` handlers or `javascript:` URLs; never add `'unsafe-inline'` to `script-src`.

## Finding 2 — `style-src 'unsafe-inline'` (the remaining gap)

Present in every variant: `['style-src', "'self' 'unsafe-inline' https://fonts.googleapis.com"]`.

Inventory (as of this audit, across `public/*.html`):

- **~559 inline `style="…"` attributes** (top offenders: `flow.html` 67, `control.html` 59, `event.html` 35, `plan.html` 34, `quotes.html` 29). Many are **generated in JS templates** (e.g. `style="background-image:url('${cssUrl(u)}')"` in `invite.html`, progress bars, dynamic widths/colors).
- **~46 `<style>` blocks** (one per page, mostly a single page-level stylesheet block).

Why it cannot simply be removed:

- CSP **style hashes/nonces cover `<style>` blocks only**, not inline `style="…"` **attributes**. Inline style *attributes* are only re-permitted by `'unsafe-hashes'` + per-value hashes, which is brittle and impractical for hundreds of dynamic values.
- So dropping `'unsafe-inline'` from `style-src` would immediately break every dynamic inline style (backgrounds, progress bars, show/hide width tweaks) across the app.

**Risk rating of leaving it:** Low. `style-src 'unsafe-inline'` enables CSS-injection style attacks (data exfil via CSS, UI redress) only if an attacker can already inject markup — and the app's HTML sinks are `esc()`-guarded and (for media) scheme-allowlisted, with `script-src` locked down. It is a defence-in-depth gap, not an open hole.

## Progressive plan to remove `style-src 'unsafe-inline'`

Forward-only, each step independently shippable and testable. Do **not** attempt in one pass.

1. **Freeze new inline styles.** Add a lint/check (mirroring the `csp-hashes` approach) that fails CI on *new* `style="…"` attributes, so the count only goes down. Allowlist the few truly-dynamic sinks.
2. **Hash the `<style>` blocks.** Extend `scripts/csp-hashes.cjs` to also emit `'sha256-…'` for each page-level `<style>` block and feed them into a `style-src` hash list (same machinery as scripts). This lets the `<style>` blocks stay inline without `'unsafe-inline'` — but only *after* step 4, since attributes still need it.
3. **Migrate static inline attributes → classes.** Replace fixed `style="…"` (non-dynamic) with utility classes in each page's `<style>` block. This is the bulk of the ~559 and is mechanical per page. Start with the heaviest: `flow.html`, `control.html`, `event.html`, `plan.html`, `quotes.html`.
4. **Convert dynamic inline styles → CSS custom properties.** For the genuinely dynamic cases, set a CSS variable via `el.style.setProperty('--w', pct)` is itself an inline-style write and still needs the directive; instead prefer `classList` toggles + `<style>`-defined rules, or set the property on a small set of elements and cover with `'unsafe-hashes'` as a last resort. Audit `background-image:url()` sinks to keep them scheme-allowlisted (already done for `invite.html` / `proposal-view.html`).
5. **Flip the directive.** Once inline `style=` attributes are gone (or down to an allowlisted, hashed handful) and `<style>` blocks are hashed, change `style-src` to `'self' <style-hashes> https://fonts.googleapis.com` in `CSP_BASE`, run `npm run gen:csp` + `npm run check:csp`, and rely on `headers-parity` + an e2e visual pass to confirm nothing broke.

## Safe reductions made in this pass

None to the policy itself — removing or tightening `style-src` now would break rendering, and no trivially-safe reduction exists without the migration above. The CSP was **regenerated** (`npm run gen:csp`) only to pick up the new inline-script hash from the `invite.html` render-side scheme-allowlist fix (a security hardening, not a weakening); `script-src` stays hash-only with no `'unsafe-inline'`.
