# Monitoring and alerting - round 21 readiness

What is now in code (branch `fix/r21-security`) and what the owner switches on. Nothing below sends an e-mail or
calls an outside service until the owner sets it up.

## 1. CSP violation reports (built, active once the edge function is deployed)

- Every production page's Content-Security-Policy now ends with
  `report-uri https://nqltzgiwznphugcfhmbm.supabase.co/functions/v1/csp-report`. This is generated by
  `scripts/gen-csp.mjs` and `scripts/csp-hashes.cjs` (`CSP_REPORTS = true`). The staging site
  (helm-v01.vercel.app) and localhost do not report.
- `supabase/functions/csp-report` writes one redacted log line per violation, in this shape:
  `csp-violation enforce script-src-elem blocked=https://evil.example/x.js page=https://www.helm.events/sharma/quote/:id`.
  - No query strings, tokens, UUIDs, e-mails, script samples or IPs are logged.
  - Nothing is stored in the database.
  - The function always answers 204.
  - Limits: 16 KB per report, 30 reports per minute per IP, at most 10 violations per request.
- **Owner:** `supabase functions deploy csp-report --no-verify-jwt --project-ref nqltzgiwznphugcfhmbm`.
  Until it is deployed, browsers get a 404 for their report. That is harmless and visitors do not see it.
- **Read the reports:** Supabase -> Edge Functions -> `csp-report` -> Logs (search `csp-violation`). Review them weekly.
  Expect occasional noise from browser extensions (`blocked=chrome-extension`). A real problem looks like
  `script-src` blocking a Helm page's own script after a deploy.
- **Switch off:** `supabase secrets set HELM_CSP_REPORTS_ENABLED=false` (no redeploy needed), or set `CSP_REPORTS = false`
  in `scripts/csp-hashes.cjs` and run `node scripts/gen-csp.mjs`.

## 2. Front-end error monitoring - Sentry (built, OFF until a DSN is set)

- `public/telemetry.js` already redacts tokens, UUIDs, e-mails, phone numbers and OTPs, and loads the SRI-pinned
  Sentry 8.35.0 bundle only when a DSN exists. Since r21 it reads the DSN after `config.js` has loaded.
  Before, it read too early and a DSN placed in `config.js` was never picked up.
- **Owner:**
  1. In Sentry, go to Create project -> Browser JavaScript, then Settings -> Client Keys (DSN). Copy the DSN.
  2. Paste it into `public/config.js` -> `window.HELM_TELEMETRY.dsn`.
  3. Run `node scripts/gen-csp.mjs`. It adds the DSN's EXACT ingest host (for example `https://o123.ingest.us.sentry.io`)
     to `connect-src` in `vercel.json` and `public/_headers`. `server.js` reads the same file. CI refuses a wildcard host.
  4. Bump `config.js` (`node scripts/bump-changed-assets.mjs --base origin/main --apply`), then commit and deploy.
- In Sentry, add an alert rule: "A new issue is created" -> e-mail or phone.

## 4. Security alert e-mails - `security-alert-mailer` (built, DORMANT)

These are already queued in the database by migration 0054 (`security_alert_outbox`): role changes, admin overrides,
lockouts, HQ operator changes. The bell and HQ "Security" panel show them today. The mailer only adds e-mail.

Readiness checklist:

1. [ ] Confirm 0054 is applied: `select to_regclass('public.security_alert_outbox') is not null;` should return true.
2. [ ] Deploy: `supabase functions deploy security-alert-mailer --no-verify-jwt` (also declared in `supabase/config.toml`).
3. [ ] Set the secrets: `HELM_SECURITY_ALERT_SECRET=<long random>` and `HELM_SECURITY_ALERT_HQ_TO=security@helm.events`.
   The mail transport uses the shared SMTP or Resend secrets already used by the other mailers.
4. [ ] Schedule it every 5 minutes (SQL editor, `pg_cron` + `pg_net`):
   ```sql
   select cron.schedule('security-alert-mailer', '*/5 * * * *', $$
     select net.http_post('https://nqltzgiwznphugcfhmbm.supabase.co/functions/v1/security-alert-mailer',
       headers := jsonb_build_object('x-helm-cron-secret', '<same secret>', 'content-type', 'application/json'),
       body := '{}'::jsonb) $$);
   ```
5. [ ] Turn it on: `supabase secrets set HELM_SECURITY_ALERTS_ENABLED=true`.
6. [ ] Test it: in a test studio, change a teammate's role. Within 5 minutes the studio admins get an e-mail.
   An HQ operator add or remove e-mails `security@helm.events`.
7. [ ] Make sure the `security@helm.events` mailbox or group exists and someone reads it (Google Admin -> Groups).
