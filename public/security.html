Security & Trust

An overview of the technical and organisational measures that keep each studio's workspace private and available.

Last updated: October 16, 2026

On this page 1. Our approach 2. Tenant isolation 3. Encryption 4. Application security 5. Account and staff access 6. Backups and availability 7. Incident response 8. Responsible disclosure

1. Our approach

Security is built into how Helm stores data, not added later. This page summarises our measures; the binding commitments are in the Data Processing Addendum (Annex: security measures). We do not currently hold a third-party certification such as ISO/IEC 27001 or SOC 2 [OWNER TO FILL: update if certified].

2. Tenant isolation

  • Every studio is a separate tenant. PostgreSQL row-level security (RLS) policies scope every table to the signed-in user's studio, enforced by the database itself, not only the app.
  • Role-based access control with a configurable permission matrix; studio owners decide what each role can see and change.
  • Client links (proposals, approvals, invitations) use unguessable, expiring tokens and are not indexed by search engines.

3. Encryption

  • TLS 1.2+ for all traffic, with HSTS.
  • Data encrypted at rest by our hosting provider (AES-256).
  • Passwords are never stored in plain text; authentication is handled by Supabase Auth with salted hashing.

4. Application security

  • Strict Content Security Policy with Trusted Types, no inline scripts, and hashed allow-lists.
  • Server-side validation and pricing authority; the browser is never trusted for money calculations.
  • Upload checks and quarantine for files.
  • Automated test suites run before every release, and periodic security reviews against the OWASP Top 10.

5. Account and staff access

  • Multi-factor authentication available for accounts; required for Helm administrator access.
  • Account lockout and alerts on suspicious sign-in activity.
  • Least-privilege staff access; production access is logged.
  • An audit log in each workspace records who changed what.

6. Backups and availability

Daily automated database backups with point-in-time recovery as provided by our database host [OWNER TO FILL: confirm backup plan and retention]. Service targets are in our Service Level Agreement.

7. Incident response

We maintain an incident response process. Where a personal data breach affects your data we will notify you without undue delay and in time for you to meet your legal deadlines: the Data Protection Board of India (intimation without delay and a detailed report within 72 hours under DPDP Rules, r. 7), EU/UK supervisory authorities (72 hours, GDPR / UK GDPR Art. 33), CERT-In (6 hours for reportable cyber incidents under its 28 April 2022 Directions), the UAE Data Office (PDPL Art. 9) and US state breach laws as applicable.
