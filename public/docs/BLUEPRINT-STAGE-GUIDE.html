1 · What Blueprint Stage is

Blueprint Stage is an end-to-end event operating system for event studios and agencies. One platform carries an event from the first enquiry all the way to the final profit-and-loss statement — capturing the lead, designing the floor in 2D and 3D, quoting and confirming, planning the menu and tasks, assigning crew and resources, running the event day, and closing the books.

It is built as a set of focused single-purpose pages backed by a shared data layer (store-api.js) talking to a Supabase (PostgreSQL) backend. Access is governed by row-level security so each role sees exactly what it should — and, as of Block F, each studio is fully isolated from every other studio on the same installation.

🎯 SellCapture leads, nurture them, build proposals, quote, and get client sign-off.
📐 DesignDrag-and-drop 2D floor plans, walk them in 3D, 12 templates, auto-priced.
🗂️ PlanMenu & dish catalog, task templates, checklists, milestones, readiness gates.
📦 OperateCrew, staff suggestions, inventory, vendors, logistics, live event-day view.
💳 SettleBudget vs actuals, invoices, settlement, closure with a clean P&L.
🛡️ GovernPer-role access matrix, audit log, insights, reports, in-app notifications.

2 · Roles & access control (RBAC)

Every user belongs to a studio and holds one role. A configurable access matrix (edited in Control Center) decides, for each role, what it can do in each functional area — none, view, or edit. The matrix has 11 roles × 26 areas = 286 rules, and it is enforced in the database itself through the has_area(area, need) helper wired into every table's row-level-security policy. The UI simply reflects what the database will allow.

RoleTypical scope
AdminEverything, including the access matrix, pricing config, org settings.
PlannerLeads → plan → operations; the core producer role.
SalesLeads, CRM, proposals, quotes; limited operational view.
OperationsResources, inventory, logistics, run-sheet; no finance.
CrewEvent-day tasks and equipment only (mobile view); no finance, no pricing.
ClientTheir own event only, via the client portal (read-only).
…plus finance / vendor / QA-style roles, all matrix-configurable.
Why this matters: access is checked at the data layer, not just the screen. Even if someone hit the API directly, Operations and Crew read zero finance rows — verified live during the security pass.

5 · Step-by-step: a lead all the way to close

This is the canonical path a producer follows. Every step names the page you go to and what happens next.

1
Capture the lead — Home → Leads (leads.html). Add the enquiry: client name, contact, event type, tentative date, headcount, budget. It lands as a Lead.
2
Qualify & discover — open the lead → Discovery (discovery.html). Record the brief, venue, constraints. Not a fit? Mark it lost (Nurture can re-engage later).
3
Pitch the concept — Proposal (proposal.html): theme, palette, scope, reference images. Publish it → the client can view it at proposal-view.html.
4
Design the floor — Builder (builder.html): start from a template or blank, drag stages/seating/tables to scale, check it in 3D. Each save is versioned.
5
Quote & send — Quotes (quotes.html): the layout + pricing config produce line items and a total. Generate the client approval link.
6
Client confirms — the client opens Approve / Portal (approve.html / portal.html) and approves. The event flips to Confirmed and the quote locks.
7
Plan the menu — Plan (plan.html): write package notes and use the dish search to add dishes (with optional quantities). Confirm to lock the menu.
8
Break down the work — task templates seed the task list; on Operations (ops.html) assign each task in-house or outsource to a vendor. Use Suggested crew to pick people by skill + availability.
9
Reserve resources — Inventory/Resources: raise stock requests for chairs, mics, props; Logistics for transport.
10
Go / no-go — Ready (ready.html): the readiness gate confirms everything is in place. Check the Calendar for clashes.
11
Run the day — Run-sheet + Command drive the schedule; crew work from work.html on their phones, ticking tasks and checking kit in/out; log problems in Issues; upload photos to Media.
12
Tear down — Teardown (teardown.html): return equipment; inventory reconciles.
13
Settle & close — Budget → Settlement → Closure: reconcile actual costs and payments, then close with a final P&L. Insights rolls it into trend analytics.

6 · Worked example A — “Sharma Wedding, 12 Dec”

Scenario: A bride's family enquires about a 300-guest wedding on 12 December, budget ₹18 lakh.

Lead→Discovery→Proposal→2D/3D quote→Approved→Menu+crew→Event day→Closed P&L
  1. Leads: Priya (Sales) logs the enquiry → event code 12122026-01 is created.
  2. Discovery: site visit notes — banquet hall, 300 pax, mandap + stage + dining.
  3. Proposal: “Marigold & Ivory” theme, palette, 6 reference images. Published; the family opens the proposal link and loves it.
  4. Builder: Priya starts from the Wedding template, lays a mandap, a stage, 30 round tables of 10, and a buffet line — then checks sightlines in 3D.
  5. Quote: the layout + plate/chair rates produce ₹17.4 L. She sends the approval link.
  6. Confirmed: the family approves in the portal → event locks, stage = Confirmed. A 🔔 notification tells the planner.
  7. Plan / menu: the planner searches the dish catalogue — “paneer”, “biryani”, “gulab” — adds ~24 dishes, sets quantities for live counters, and confirms (menu locks).
  8. Operations: 182 seeded tasks appear; catering is outsourced to “Annapurna Caterers” (🤝 badge), décor stays in-house. Suggested-crew proposes 3 available decorators; one already clashes on 12 Dec, so the tool warns and she picks another.
  9. Resources: 300 chairs + 30 tables + PA reserved; logistics books two tempos.
  10. Ready: readiness gate is green; calendar shows no clash.
  11. Event day: crew open work.html, tick setup tasks, check the PA in; one issue (a late florist) is logged and resolved; 40 photos uploaded — a few surface in the family's portal gallery.
  12. Closure: actuals ₹15.9 L vs ₹17.4 L billed → ~₹1.5 L margin; closed. Insights adds it to the season's win/loss trend.

7 · Worked example B — corporate conference + outsourcing a task

Scenario: A tech firm books a 1-day, 150-seat conference. This example focuses on the operations mechanics — outsourcing and staff suggestions.

  1. Fast-track sell: the client already has a brief, so Sales goes Lead → Quote quickly using the Conference template (rows of theatre seating + a keynote stage).
  2. Confirmed & planned: approved; light menu (working lunch + tea counters) added from the catalogue.
  3. Outsource A/V: on Operations, the “Stage & A/V” task category is set to Outsource → vendor “BrightLine AV”. Every task in that category now carries the 🤝 badge, so on the day everyone knows it's a partner's responsibility.
  4. Staff by skill + availability: for “Registration desk”, the Suggested crew bar lists people whose skills match and who are free that date. One suggestion shows a clash warning (already on another event) — the tool won't silently double-book; the coordinator picks two free staff instead.
  5. Pre-commit clash check: when assigning, a “would clash” warning appears before the assignment is saved, not after.
  6. Day + close: crew run from mobile; BrightLine's outsourced tasks are tracked alongside in-house ones; settlement reconciles BrightLine's bill; closure produces the P&L.

8 · How multi-tenant works

Block F turned Blueprint Stage from a single-studio app (“Helm”) into a platform that can host many isolated studios on one database — each seeing only its own data, with its own branding, currency and timezone. All of Helm's existing data was preserved and re-homed under a default Helm Studio org; nothing was deleted.

The model: shared database, strict isolation

Every tenant table carries an org_id. Row-level security appends and org_id = current_org_id() to every read and write, where current_org_id() is a security-definer function that reads the signed-in user's org from their profile. The result: two studios can share one table and never see each other's rows.

Creating a new studio (self-serve onboarding)

1
Sign up: on the login page, the “Create studio” tab takes a studio name, email and password.
2
create_studio() runs: it makes a new organization, sets the signer as its admin, and seeds clean curated defaults — the role matrix, task & checklist templates, plate/chair/dish catalogues, nurture templates and default pricing — copied from Helm's library minus any test rows. No contacts, staff, vendors, inventory or events are copied.
3
Land in an empty workspace: the new studio starts with a full catalogue to work from but zero operational data of its own.
4
Brand it: in Control Center → Organization settings, set business name, email, logo, accent colour, currency, timezone and GSTIN. Client-facing pages (the portal) then show that studio's brand.
Proven, not assumed. A live isolation test created a fresh studio and confirmed it: got its own org_id (not Helm), was seeded with 134 dishes / plate & chair types / 182 task templates / the full 286-row role matrix, had zero test rows leak in, and read 0 of Helm's quotes, leads, costs, inventory, tasks and crew.

What made isolation safe

  • Auto-stamping: org_id defaults to current_org_id(), so new rows are tagged automatically.
  • Anon flows: the client portal and crew links are public (no session) — they resolve the org from the parent record via a trigger, never from the caller.
  • Per-studio uniqueness: codes and names (quote codes, vendor names, dish names, the role matrix, pricing keys, task/nurture templates) are unique within a studio, so two studios can both have a “Wedding” template or a “Paneer Tikka” dish.
  • Nothing deleted: Helm's data is intact under the Helm org; the free-text menu notes box was kept alongside the new dish catalogue.

11 · Data protection, privacy & transparency

We want to be fully open about what is protected today, what is not done yet, and what depends on others. No system is ever “100% secure”, and anyone who says so is wrong — so here is the honest picture, kept up to date as gaps are closed.

What is protected today (proven)

  • Studio isolation — enforced by Postgres Row-Level Security in the database itself, not app code. Verified live: a brand-new studio read 0 of another studio's quotes, leads, costs, inventory, tasks and crew.
  • Role-based access — the 286-rule matrix limits every role; Operations and Crew read 0 finance rows (verified).
  • Server-side authority — sensitive writes run through SECURITY DEFINER functions that stamp the studio id themselves, so the client can't forge which studio it writes to.
  • Every row belongs to a studio — org_id is now NOT NULL on the core tables (Phase 60).
  • Abuse protection — per-IP rate limiting on the app's own API, plus Supabase's auth rate limits for sign-in / OTP / sign-up.
  • Hardening basics — security headers (CSP, HSTS, anti-clickjacking and more), an audit log across 16 tables, and Supabase-managed password hashing (we never handle raw passwords).

What we depend on

Your data lives in Supabase (managed PostgreSQL). We rely on their infrastructure, backups and internal access controls — a reasonable, industry-standard dependency, but still a third party. A platform-level incident on their side would affect our data as it would any tenant on a managed service.

Isolation is not the same as privacy

Isolation stops Studio A from ever seeing Studio B — that is done and proven. Privacy law is a separate, broader duty: telling people what you collect and why, keeping consent records, letting them see and delete their data, deleting it when it's no longer needed, and reporting breaches on time. For an India-facing business the relevant law is the Digital Personal Data Protection (DPDP) Act, 2023. That compliance layer is not built yet and should be in place before handling real customers' personal data at scale.

Our commitment. We won't claim a security guarantee we haven't tested, we label what's proven versus pending honestly, and we keep this section current as each gap is closed.
