1 · The one customer flow

Everything below happens on a single screen — public/flow.html — opened when you click Generate a quote (Home) or Convert (Leads). No more hopping between pages and back. The old per-page screens remain as the "Open → full workspace" view for operations, tasks and assignments after approval.

Client & event → Discovery → Requirements → Venue → Menu package → Floor layout → Proposal → Quotation → Send for approval, with a sticky live price rail and a step checklist. Data auto-fills from the lead and autosaves through the same APIs the individual pages use, so nothing is duplicated.

2 · The 13 requirements — status & how to work on each

1

Default layout generation

Done

Enter event type + guests + hall length/breadth in the flow's Floor layout step → Generate default layout opens the 2D builder pre-filled and produces default variants (stage, seating, walkway, buffet, dance floor…) scaled to the headcount and hall size. The planner picks one and edits freely.

flow.html #genLayout → builder.html?gen=1&type=&guests=&len=&wid= → runCustomGenerate() / generateVariants() · TEMPLATES presets · EVENT_TYPE_PRESET.

Next: make the generation scale rules data-driven (see #4) instead of the current in-code generator maths.

2

Event categories & types hierarchy

To build

A structured tree: Private / Corporate / Public / Sports… → individual event types under each. Today "event type" is a free-text/preset string.

How to build: new table event_categories(id, org_id, category, type, seq, active) (multi-tenant, cfg-style RLS like dish_catalog); seed a starter tree; Control Center CRUD; the flow's event-type field becomes a category→type dropdown. Mirror the phase62 pattern exactly.

3

Layout editable after generation

Done

The 2D builder is fully editable — drag/drop, add/remove, resize, rotate, multi-select. The generated layout is a starting point, not fixed.

builder.html — SVG canvas, ASSETS catalogue (~70 items), undo/redo, 3D preview.

4

Event-specific default rules

To build

Embed experienced planners' knowledge as numbers: seats per guest, buffet tables per N guests, stage size by headcount, walkway, DJ/lighting, etc. — different per event type, and changeable by an admin, not a developer.

How to build: a layout_rules JSON per event type in app_config (admin-editable in Control Center), e.g. { chairsPerGuest:1, buffetPer:75, stage:true, danceFloor:true, walkway:true, aislePct:12 }. The generator reads the rule for the chosen type + guest count instead of hardcoded maths. Requires the domain data in §4.

5

Dynamic pricing / cost breakdown

Done

One shared pricing engine drives the builder panel, the flow's live rail and the quote — always the same number. Chairs priced per seat, every object per unit, catering = guests × the menu package's plate price, + layout/setup + GST. Add/remove anything and the total moves live. Every rate is admin-editable in Control Center.

store-api.js BPStore.pricing (breakdown / quoteTotal / fromItems) · builder renderPrice · quotes calcPricing (delegates) · Control Center "Object & item prices" + "Menu packages".

6

Backdrop / decoration selection (by stage size)

To build

After the layout, choose a stage backdrop from a library of past-event photos / AI designs — showing only designs that suit the stage dimensions (no small backdrop for an 80-ft stage).

How to build: table backdrops(id, org_id, name, image_url, min_w, max_w, tags); a flow step that reads the stage object's width from the layout and filters the library by min_w ≤ stageW ≤ max_w. Images stored in Supabase Storage / an assets bucket. AI generation is a later enhancement.

7

3D visualisation (with backdrop)

Partial

The builder already renders the same layout in 3D (Three.js). Missing: dropping the chosen backdrop image onto the stage in that 3D view so the client sees the real proposed scene.

How to build: map the selected backdrop image as a texture on a plane behind/above the stage model in the existing 3D scene; start with sample designs for a few common stage sizes for the MVP.

8

PDF / quotation generation

Partial

The quote screen already produces a printable quote/invoice (downloadQuote), and the builder exports the layout as PNG. Missing: a one-click combined PDF (quotation + venue layout) surfaced inside the flow, plus share.

How to build: add "Download quote PDF" and "Download layout PDF" buttons to the flow; use the browser's print-to-PDF of a print stylesheet (no new dependency) or a small client-side PDF lib served locally.

9

Quotation versioning (Q1, Q2, Q3…)

Partial

Layout revisions are already versioned (quote_versions). Missing: labelling the pricing revisions as Q1/Q2/Q3 and keeping each rather than overwriting quote.pricing.

How to build: table quotation_versions(id, org_id, quote_id, label 'Q1', pricing jsonb, created_at, created_by); snapshot on each "Save quotation"; show the history in the flow. Never overwrite — always append.

10

Advance payment → confirmed booking

Partial

Building blocks exist: the client approval flow (OTP + consent), createPayment (simulated link now; Razorpay Edge Function when keys are added), mark_paid, payment_milestones, and a simulated pay page. Missing / to finish: accepting a quote must not confirm the booking — an advance/token step must gate it; support both online (gateway on the tenant account) and offline (admin records cash + receipt no.); generate a receipt each time.

How to build: after approval, show an advance-payment card (10% default, editable); online → payment link; offline → "Record cash / receipt no." form → mark_paid with a receipt row; only then set status = confirmed & stage = planning (stage auto-advance is already wired). Real gateway needs the tenant's keys (owner action).

11

Complete communication / activity trail

Partial

Underlying records exist: audit_log, quote_consents, quote_payments, notifications. Missing: one consolidated, human-readable timeline per event — quote versions, discounts, advances, receipts, edits — to settle any dispute.

How to build: an "Activity" panel on the flow / workspace that merges those sources ordered by time.

12

Customer + planner acknowledgement

Partial

notifications exists. Missing: explicit both-sides messages — customer gets "payment received, booking processing"; planner gets "client accepted & paid the advance".

How to build: on mark_paid, insert a notification for the planner and surface a confirmation on the client portal; email/WhatsApp optional.

13

Admin-configurable defaults (no code change)

Partial

Pricing is already admin-editable. To finish: event categories (#2) and layout rules (#4) must be edited in Control Center too, so defaults change without a developer. All of it stays per-tenant via org_id.

3 · Admin-configurable (no-developer) defaults

The principle for the MVP: anything an experienced planner would tune, an admin edits in Control Center — never in code. Already no-code: chair/plate rates, per-object prices, layout/setup fee, GST, menu packages & their dish lists & plate prices, coupons, vendors, the role/access matrix. To make no-code next: event categories/types, layout default rules, backdrop library, advance-payment %.

Storage pattern: per-tenant tables (with org_id + cfg-style RLS) for lists, and JSON blobs in app_config for rule sets. New studios inherit clean defaults automatically via create_studio (add each new library table to its copy list, as done for menu packages).

6 · How to work on this repo

  • Architecture: 37 vanilla-JS single-file pages in public/ + one shared data layer public/store-api.js (the BPStore facade) over Supabase (Postgres + RLS + SECURITY DEFINER RPCs). No build step, no framework.
  • Run locally: node server.js → http://localhost:4173. Sign in with your studio admin.
  • Multi-tenant: every row carries org_id; RLS filters by current_org_id(). New library tables must be added to create_studio so new studios inherit them.
  • Migrations: each change is a numbered supabase/phaseNN-*.sql, idempotent, run in the Supabase SQL editor. Front-end has a graceful fallback until the SQL is run.
  • Cache busting: when store-api.js changes, bump ?v= on every page that loads it.
  • One flow, one price: new pricing must go through BPStore.pricing; new pre-approval fields belong in flow.html and should autosave through existing BPStore calls.
  • Never remove features. Everything is additive; the per-page screens stay as the post-approval workspace.
