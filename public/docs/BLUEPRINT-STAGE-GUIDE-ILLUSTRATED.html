1 · What Blueprint Stage is

Blueprint Stage is an end-to-end event operating system for event studios and agencies. One platform carries an event from the first enquiry to the final profit-and-loss — capturing the lead, designing the floor in 2D and 3D, quoting and confirming, planning the menu and tasks, assigning crew and resources, running the event day, and closing the books. It is a set of focused pages over a shared data layer (store-api.js) talking to Supabase (PostgreSQL), with database-level row security so every role — and every studio — sees exactly what it should.

🎯 SellCapture leads, nurture them, build proposals, quote, and get client sign-off.
📐 DesignDrag-and-drop 2D floor plans, walk them in 3D, 12 templates, auto-priced.
🗂️ PlanMenu & dish catalogue, task templates, checklists, milestones, readiness gates.
📦 OperateCrew, staff suggestions, inventory, vendors, logistics, live event-day view.
💳 SettleBudget vs actuals, invoices, settlement, closure with a clean P&L.
🛡️ GovernPer-role access matrix, audit log, insights, reports, in-app notifications.

2 · Roles & access control (RBAC)

Every user belongs to a studio and holds one role. A configurable access matrix decides, per role and per functional area, whether it can do nothing, view, or edit — 11 roles × 26 areas = 286 rules, enforced in the database through has_area(area, need) wired into every table's row-security policy. The UI only ever reflects what the database will allow.

RoleTypical scope
AdminEverything: the access matrix, pricing config, org settings.
PlannerLeads → plan → operations; the core producer role.
SalesLeads, CRM, proposals, quotes; limited operational view.
OperationsResources, inventory, logistics, run-sheet; no finance.
CrewEvent-day tasks and equipment only (mobile view).
ClientTheir own event only, via the read-only portal.
Enforced at the data layer, not just the screen. Even calling the API directly, Operations and Crew read zero finance rows — verified live during the security pass.

5 · Step-by-step: a lead all the way to close

The canonical path a producer follows. Each step names the page and what happens next.

1
Capture the lead — Home → Leads. Add the enquiry (client, contact, event type, date, headcount, budget). It lands as a Lead with an auto event code like 12122026-01.
2
Qualify & discover — Discovery: record the brief, venue and constraints. Not a fit? Mark it lost (Nurture can re-engage later).
3
Pitch the concept — Proposal: theme, palette, scope, references. Publish → client views it.
4
Design the floor — Builder: template or blank, drag stages/seating/tables to scale, check in 3D. Each save is versioned.
5
Quote & send — Quotes: layout + config produce line items and a total; generate the approval link.
6
Client confirms — the client approves in the Portal; the event flips to Confirmed and the quote locks. The planner gets a 🔔.
7
Plan the menu — Plan: package notes + dish search (with quantities). Confirm to lock the menu.
8
Break down the work — task templates seed the list; on Operations assign in-house or outsource, and use Suggested-crew (skill + availability).
9
Reserve resources — Inventory/Resources raise stock requests; Logistics books transport.
10
Go / no-go — Ready confirms everything's in place; check the Calendar for clashes.
11
Run the day — Run-sheet + Command drive the schedule; crew work from work.html on phones; log Issues; upload to Media.
12
Tear down — Teardown: return equipment; inventory reconciles.
13
Settle & close — Budget → Settlement → Closure: reconcile actuals and payments, close with a final P&L; Insights folds it into trends.

6 · Worked example A — “Sharma Wedding, 12 Dec”

Scenario: a family enquires about a 300-guest wedding on 12 December, budget ₹18 lakh.

Lead→Discovery→Proposal→2D/3D quote→Approved→Menu+crew→Event day→Closed P&L
  1. Leads: Priya (Sales) logs the enquiry → code 12122026-01 is created.
  2. Discovery: site visit — banquet hall, 300 pax, mandap + stage + dining.
  3. Proposal: “Marigold & Ivory” theme, palette, 6 references. The family opens the link and loves it.
  4. Builder: start from the Wedding template, lay a mandap, stage, 30 round tables of 10, a buffet line; check sightlines in 3D.
  5. Quote: layout + plate/chair rates → ₹17.4 L; send the approval link.
  6. Confirmed: the family approves in the portal → event locks, stage = Confirmed; the planner is notified.
  7. Plan / menu: search “paneer”, “biryani”, “gulab”, add ~24 dishes, set live-counter quantities, confirm (menu locks).
  8. Operations: 182 seeded tasks appear; catering is outsourced to “Annapurna Caterers” (🤝), décor stays in-house. Suggested-crew flags one decorator who clashes on 12 Dec, so she picks another.
  9. Resources: 300 chairs + 30 tables + PA reserved; two tempos booked.
  10. Ready: gate green, no calendar clash.
  11. Event day: crew tick setup tasks on their phones, check the PA in; a late-florist issue is logged and resolved; 40 photos uploaded, some to the family's portal.
  12. Closure: actuals ₹15.9 L vs ₹17.4 L billed → ~₹1.5 L margin; closed. Insights adds it to the season trend.

7 · Worked example B — corporate conference + outsourcing

Scenario: a tech firm books a 1-day, 150-seat conference — focus on the operations mechanics.

  1. Fast-track sell: the brief is ready, so Sales goes Lead → Quote quickly using the Conference template (theatre seating + keynote stage).
  2. Confirmed & planned: approved; a light menu (working lunch + tea counters) added from the catalogue.
  3. Outsource A/V: on Operations, the “Stage & A/V” category is set to Outsource → vendor “BrightLine AV”; those tasks now carry the 🤝 badge so everyone knows it's a partner's job.
  4. Staff by skill + availability: for “Registration desk”, Suggested-crew lists people whose skills match and who are free that date; one shows a clash warning, so the coordinator picks two free staff instead.
  5. Pre-commit clash check: a “would clash” warning appears before the assignment is saved, not after.
  6. Day + close: crew run from mobile; BrightLine's outsourced tasks track alongside in-house ones; settlement reconciles their bill; closure produces the P&L.

8 · How multi-tenant works

Block F turned Blueprint Stage from a single-studio app (“Helm”) into a platform hosting many isolated studios on one database — each seeing only its own data, with its own branding, currency and timezone. All existing data was preserved under a default Helm Studio org; nothing was deleted.

The model: shared database, strict isolation

Every tenant table carries an org_id. Row security appends and org_id = current_org_id() to every read and write, where current_org_id() reads the signed-in user's org from their profile. Two studios share one table and never see each other's rows.

Creating a new studio (self-serve onboarding)

1
Sign up via the “Create studio” tab.
2
create_studio() runs: makes a new organization, sets the signer as its admin, and seeds clean curated defaults — the role matrix, task & checklist templates, plate/chair/dish catalogues, nurture templates and default pricing — copied from Helm's library minus any test rows. No contacts, staff, vendors, inventory or events are copied.
3
Land in an empty workspace with a full catalogue to work from but zero operational data.
4
Brand it in Control Center → Organization settings (name, email, logo, accent, currency, timezone, GSTIN). Client pages then show that studio's brand — as the portal screenshot above shows.
Proven, not assumed. A live isolation test created a fresh studio and confirmed it: got its own org_id (not Helm), was seeded with 134 dishes / plate & chair types / 182 task templates / the full 286-row role matrix, had zero test rows leak in, and read 0 of Helm's quotes, leads, costs, inventory, tasks and crew.

What made isolation safe

  • Auto-stamping: org_id defaults to current_org_id(), so new rows are tagged automatically.
  • Anon flows: the client portal and crew links are public (no session) — they resolve the org from the parent record via a trigger, never from the caller.
  • Per-studio uniqueness: quote codes, vendor/dish names, the role matrix, pricing keys and task/nurture templates are unique within a studio — two studios can both have a “Wedding” template or a “Paneer Tikka” dish.
  • Nothing deleted: Helm's data is intact under the Helm org; the free-text menu notes box was kept alongside the new dish catalogue.

11 · Data protection, privacy & transparency

We want to be fully open about what is protected today, what is not done yet, and what depends on others. No system is ever “100% secure”, and anyone who says so is wrong — so here is the honest picture, kept up to date as gaps are closed.

What is protected today (proven)

  • Studio isolation — enforced by Postgres Row-Level Security in the database itself, not app code. Verified live: a brand-new studio read 0 of another studio's quotes, leads, costs, inventory, tasks and crew.
  • Role-based access — the 286-rule matrix limits every role; Operations and Crew read 0 finance rows (verified).
  • Server-side authority — sensitive writes run through SECURITY DEFINER functions that stamp the studio id themselves, so the client can't forge which studio it writes to.
  • Every row belongs to a studio — org_id is now NOT NULL on the core tables (Phase 60).
  • Abuse protection — per-IP rate limiting on the app's own API, plus Supabase's auth rate limits for sign-in / OTP / sign-up.
  • Hardening basics — security headers (CSP, HSTS, anti-clickjacking and more), an audit log across 16 tables, and Supabase-managed password hashing (we never handle raw passwords).

What we depend on

Your data lives in Supabase (managed PostgreSQL). We rely on their infrastructure, backups and internal access controls — a reasonable, industry-standard dependency, but still a third party. A platform-level incident on their side would affect our data as it would any tenant on a managed service.

Isolation is not the same as privacy

Isolation stops Studio A from ever seeing Studio B — that is done and proven. Privacy law is a separate, broader duty: telling people what you collect and why, keeping consent records, letting them see and delete their data, deleting it when it's no longer needed, and reporting breaches on time. For an India-facing business the relevant law is the Digital Personal Data Protection (DPDP) Act, 2023. That compliance layer is not built yet and should be in place before handling real customers' personal data at scale.

Our commitment. We won't claim a security guarantee we haven't tested, we label what's proven versus pending honestly, and we keep this section current as each gap is closed.
